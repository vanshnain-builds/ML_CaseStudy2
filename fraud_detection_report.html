Credit Card Fraud Detection

XGBoost on the IEEE-CIS transactions dataset — SMOTE oversampling, threshold tuning, and feature-importance interpretation
Dataset: IEEE-CIS Fraud Detection (Kaggle) — train_transaction.csv + train_identity.csv, merged on TransactionID.
Scale: 590,540 transactions, 430 raw columns → 427 modeled features after cleaning.
Fraud rate: 3.50% — a heavily imbalanced binary classification problem.

1. Class Imbalance

Fraud is rare by nature, and this dataset reflects that: only 3.50% of transactions are fraudulent. A model that just predicts "legitimate" for everything would already be 96.50% accurate while catching zero fraud — which is why accuracy is the wrong metric here, and why the class balance needs explicit handling during training (via class weighting, resampling, or both).

Fig 1. Legitimate vs. fraudulent transaction counts in the training data.

2. Data Preparation

The raw dataset has 434 columns after merging transaction and identity tables. To get a clean, fully-numeric feature matrix suitable for both XGBoost and SMOTE, the pipeline:

  • Dropped 12 columns that were >90% missing: dist2, D7, id_07, id_08, id_18, id_21, id_22, id_23, id_24, id_25, id_26, id_27
  • Engineered time features from TransactionDT (hour-of-day, day-of-week) and amount features (log-transform, decimal-cents pattern — a known fraud signal in this dataset)
  • Frequency-encoded high-cardinality identifiers (card1, card2, addr1, P_emaildomain)
  • Label-encoded the remaining 29 categorical columns (missing → -1)
  • Median-imputed remaining numeric gaps

Result: 590,540 rows × 427 features, zero missing values, ready to model.

3. Train/Test Split — Time-Based, Not Random

Instead of a random 80/20 split, the data was sorted by TransactionDT and split chronologically — the first 80% of transactions (in time) trains the model, and the last 20% tests it. This mirrors how the model would actually be deployed (predicting future transactions from past patterns) and avoids the subtle leakage a random split can introduce when the same card, device, or address appears in both the training and test rows.

4. Two Ways of Handling the Imbalance

Two XGBoost models were trained on identical features and evaluated on the exact same held-out test set, so the comparison isolates the effect of the imbalance-handling strategy:

Model A Class-weighted baseline

Standard XGBoost with scale_pos_weight = 27.5 (the ratio of legitimate to fraudulent transactions in the training set), which tells the loss function to penalize missed fraud cases proportionally more. No resampling — the model sees the real class distribution.

Model B RandomUnderSampler + SMOTE

SMOTE (Synthetic Minority Oversampling Technique) generates synthetic fraud examples by interpolating between real fraud cases and their nearest fraud neighbors in feature space, rather than just duplicating them. Run directly on the full ~472K-row training set with anywhere near full 1:1 rebalancing, this would have needed to synthesize hundreds of thousands of new rows — impractical for this environment's compute budget. So this pipeline first randomly undersamples the majority (legitimate) class down to 100,000 rows, then applies SMOTE to bring the fraud share up to a 1:2 ratio (33% fraud in the final training set, 150,000 rows total). This under+over combination is a standard, well-documented approach (available directly as imblearn.pipeline building blocks) for keeping synthetic-sample volume and training time manageable while still sharply improving the class balance the model learns from.

Finding: the class-weighted baseline (Model A) matches or slightly edges out the SMOTE pipeline (Model B) on both ROC-AUC and PR-AUC. This is a genuine and fairly common result for gradient-boosted trees: scale_pos_weight reshapes the loss function directly using the full, real data, while SMOTE's synthetic points are interpolated in a 427-dimensional space where "nearest neighbor" is a much fuzzier notion — and the under-sampling step here also discards a large majority of legitimate examples the model could otherwise have learned from. SMOTE is still a useful technique to know and apply (and is what this case study was asked to demonstrate), but "always oversample the minority class" isn't a universal rule — for tree ensembles in particular, class weighting is often a simpler, cheaper, and equally or more effective first move. The rest of this report focuses on the SMOTE model per the task brief, but the numbers above are worth keeping in mind when choosing an approach in practice.

5. Threshold Tuning

XGBoost outputs a fraud probability, not a label — the 0.5 cutoff is just a default, not a rule. Sweeping the decision threshold from 0 to 1 on the SMOTE model shows the classic precision/recall trade-off:

Fig 5. Confusion matrices at each threshold — note how far right the boundary has to move before recall gets anywhere near 90%.
Which threshold to use is a business decision, not a modeling one. Raising the threshold to 0.61 improves precision to 62.31% (fewer analysts wasting time on false alarms) but only catches 41.09% of fraud. Chasing 90% recall means accepting 39,070 false alarms against every 3,666 real fraud cases caught — roughly 10 false alarms per true catch. The right operating point depends on the relative cost of a missed fraud (chargeback, customer trust) versus a false alarm (analyst time, customer friction from a declined or flagged transaction) — a number this report doesn't have, so it's presented as a range of options rather than a single "best" answer.

6. Feature Importance & Interpretation

Two complementary views: XGBoost's built-in gain importance (how much each feature improves the model's splits, on average) and SHAP values (how much each feature pushes an individual prediction up or down, computed exactly for tree models via TreeExplainer on a 3,000-row sample of the test set).

Fig 6. Top 20 features by average gain per split.
Fig 7. SHAP summary — each dot is one transaction; color is the feature's value (red=high, blue=low), position is its impact on the fraud-probability prediction.

Reading the results

  • The Vesta-engineered V features dominate (V258, V317, V70, V126, and others). These are anonymized aggregate/velocity-style features provided by the dataset's payment processor (e.g., counts and time-deltas of related transactions), and their consistent presence at the top of both rankings confirms the model is leaning heavily on the richest engineered signal in the data — not surprising, since Vesta built them specifically for fraud detection.
  • C1, C4, C8, C11, C13, C14 (counting features — e.g. how many addresses or cards are associated with this identity) show up strongly in both views. In the SHAP plot, high values of C1 and C4 push predictions toward fraud — consistent with the intuition that an identity linked to unusually many addresses/devices is a red flag.
  • TransactionAmt and card6 (debit vs. credit) are top-5 by SHAP impact even though they don't crack the gain top-20 — a good reminder that gain (which favors features used in many high-leverage splits) and SHAP (which measures actual prediction-level impact) can disagree, and it's worth checking both. The SHAP plot shows a clear pattern for card6: one category (colored red, likely "credit") consistently pushes toward the legitimate side, while low values push toward fraud.
  • Frequency-encoded identifiers (card1_freq, P_emaildomain_freq) matter too — low-frequency card numbers or email domains (seen rarely in the training data) push toward fraud, which matches the intuition that fraud rings often use disposable or rarely-reused identifiers.

7. Summary & Recommendations

  • Both approaches beat a random classifier decisively (ROC-AUC ~0.90-0.91, versus 0.5 for chance), and reach a PR-AUC around 0.50 against a 3.50% base rate — roughly 14x better than a no-skill classifier at ranking transactions by fraud risk.
  • Class weighting (scale_pos_weight) was at least as effective as SMOTE here, and cheaper to run. For this dataset and model family, it's the recommended default; SMOTE remains worth testing for other model types (e.g. linear models, kNN) where it more directly changes what the model "sees" during training, or in combination with class weighting rather than as a replacement for it.
  • The decision threshold should be set by the fraud team, not left at 0.5 — the tuning curve in Fig 4 and the confusion matrices in Fig 5 give a menu of realistic operating points to choose from once the cost of a missed fraud vs. a false alarm is known.
  • The Vesta V-features and the C-count features are doing most of the work — any future feature-engineering effort would get the best return by extending that family (e.g. more granular velocity/aggregation windows) rather than adding unrelated data sources.
